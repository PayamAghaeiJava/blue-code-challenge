Interview preparation · code review

Wallet Project
Reviewer Report

A practical review of the current source: what is wrong, why it matters, how to improve it, and how to explain the findings in an interview.

Review approach
Findings below are based on the checked-in Java code, tests, README, and configuration. They describe visible source behavior. Each item includes evidence, impact, a repair direction, and a test idea.

Java 21 · Spring Boot 3.3.3 · Spring MVC · Spring Data JPA · H2

1. Executive review

This repository is a useful interview sample because it has a recognizable layered structure: HTTP controller → application service → Spring Data repository → JPA entities. It also includes early Kafka/KYC and notification code.

The main concern is that several core wallet paths are not reliable yet. Account creation tries to persist an account with a new, unsaved customer. Transaction mutation uses an immutable set and the relationship is not configured to cascade. Debit has both a missing request converter and a mismatch between a public UUID account number and a numeric database ID. Balance sums all amounts as positive values, so it cannot represent a net balance.

Suggested interview framing: describe the architecture fairly, then separate the requirements in the README from behavior implemented in code. Lead with reproducible correctness issues, not style preferences.

Recommended repair order

  1. Make account/customer creation and transaction persistence work.
  2. Make account identifiers consistent across the API and service.
  3. Correct balance arithmetic and enforce account/KYC/amount rules.
  4. Implement transaction history and a truly time-based, concurrent-safe limit.
  5. Make integrations, errors, security, and tests dependable.

4. Detailed findings and practical fixes

P0 · 1. Account creation references an unsaved customer

Evidence: WalletService.createAccount constructs a new Customer, assigns it to Account.owner, then saves only the account. Account.owner is a @ManyToOne without a persist cascade. There is no customer repository in WalletService.

Why it matters: JPA normally cannot insert an account row that points to a transient customer with no database ID. The save can fail. Also, creating each account creates a fresh customer object instead of finding an existing customer, contrary to “one customer can have multiple accounts.”

Solution: define whether customers are created separately or found by national code. Save or load the customer first, then attach that managed customer to the account. Add a unique constraint for national code if it is the identity key, and run the use case in a transaction.

Customer owner = customerRepository.findByNationalCode(code)
        .orElseGet(() -> customerRepository.save(newCustomer(command)));
Account account = new Account();
account.setOwner(owner);
accountRepository.save(account);

Test: create the first account for a customer, then a second account for the same national code. Assert one customer row, two account rows, and the same owner ID.

P0 · 2. Transaction collection is immutable and ledger rows are not cascaded

Evidence: account creation uses account.setTransactions(Set.of()). Credit and debit later call account.getTransactions().add(transaction). In Account, the collection uses @OneToMany(mappedBy = "account") without cascade. The foreign key is owned by Transaction.account.

Why it matters: Set.of() is immutable; adding to it throws UnsupportedOperationException. Even with a mutable collection, saving the account does not automatically persist new child transactions when no cascade is configured. The transaction is the financial ledger entry, so silently missing it is serious.

Solution: use a mutable collection (for example, HashSet) and make persistence explicit. A simple design is a TransactionRepository and saving each transaction with its account set. Alternatively, configure deliberate cascade behavior and maintain both sides through an account helper. Do not rely on changing only the inverse collection.

Transaction tx = new Transaction(requestId, account, "credit", amount);
transactionRepository.save(tx); // Transaction.account owns the FK

Test: credit an account, commit the transaction, reload it in a fresh persistence context, and assert the transaction row and account association exist.

P0 · 3. Debit request mapping and account identifier disagree

Evidence: WalletController.debitAccount asks ConversionService to convert DebitAccountRequest to DebitAccountCommand, but the repository contains no converter for that pair. The request and command define accountNumber as Long. The service calls accountRepository.findById(...). Credit instead uses a string number and findByNumber(...). Account's public number is a UUID string.

Why it matters: conversion can fail before the service runs. Even if it succeeds, debit looks up the database primary key while clients are expected to use the public UUID. Those are different identifiers.

Solution: choose one public contract. If the API uses the UUID, make debit's accountNumber a String, add a converter that maps request ID, number, and amount, and look up by public number. Return a clear not-found error with Optional rather than a null dereference.

Account account = accountRepository.findByNumber(command.getAccountNumber())
        .orElseThrow(() -> new AccountNotFoundException(...));

Test: submit a debit with a UUID account number; verify the expected account is used. Also test unknown account and malformed request handling.

P0 · 4. Balance calculation does not subtract withdrawals

Evidence: WalletService.accountBalance uses mapToDouble(Transaction::getAmount).sum(). It does not inspect the direction field. The source stores credit and debit amounts as positive numbers.

Why it matters: adding a deposit of 100 and a withdrawal of 30 returns 130; the net balance should be 70. This is a financial correctness bug. The method also puts account.getId() into the DTO field named number, although the external account number is a UUID string, and it loads all accounts before filtering.

Solution: model amount with BigDecimal and direction with an enum. Define balance as credits minus debits and calculate with decimal arithmetic. Put the account identifier in the API field that its name promises. Query only the customer's accounts in the repository.

// Illustrative after changing amount to BigDecimal and direction to an enum
BigDecimal balance = transactions.stream()
    .map(tx -> tx.getDirection() == Direction.CREDIT
        ? tx.getAmount() : tx.getAmount().negate())
    .reduce(BigDecimal.ZERO, BigDecimal::add);

Test: deposits 100 and 50, withdrawals 30; expect 120. Include no transactions, multiple accounts, and decimal values such as 0.10.

P1 · 5. Core wallet rules and caller authorization are missing

Evidence: the README requires verified customers, savings-only deposits, checking deposits and withdrawals. Credit/debit do not check verification or account type. Debit does not check positive amount or available funds. The endpoints accept account/customer identifiers from the caller, but the project has no visible authentication or ownership check.

Why it matters: requests can attempt withdrawals from savings, use unverified customers, submit negative or zero amounts, overdraw accounts, or target identifiers without proving ownership. If exposed to untrusted users, this is an authorization issue as well as a business-rule gap.

Solution: put rules in the application use case, not only in the controller. Validate amount > 0; enforce customer verification and account type; compute available funds; identify the caller from an authenticated principal and verify ownership before accessing the account. Use @Enumerated(EnumType.STRING) for account type/direction rather than relying on ordinal storage. Align the README's SAVINGS wording with the code's SAVING value.

Test: parameterize allowed and rejected cases: unverified, savings debit, checking debit within funds, overdraft, zero, negative, and a different customer's account.

P1 · 6. Balance-query limit is off by one, not daily, and not thread-safe

Evidence: WalletController holds a static HashMap. It blocks only when counter > 5. On request six, the existing count is five, so the check passes and increments to six; request seven is the first blocked. There is no date/window or expiry.

Why it matters: the README says five per day. Current behavior permits six per process lifetime, then blocks until restart. Concurrent calls can race because HashMap and the check-then-increment sequence are not atomic. A static map is also shared across tests and disappears on restart.

Solution: define which time zone and day boundary apply. Use an atomic counter with a customer-and-date key and expiry; for multiple app instances, use a shared limiter such as Redis with atomic increment. Keep rate limiting separate from caching.

Test: fifth call is accepted, sixth gets 429, next day resets, different customers have separate counts, and a parallel burst allows exactly five. Use a controllable clock and reset test state.

P1 · 7. Transaction history endpoint is a stub

Evidence: WalletService.listTransactions contains a TODO and returns Collections.emptyList(). TransactionQuery has direction and amount bounds, while the controller only supplies customer ID.

Why it matters: the endpoint always reports no activity even when transactions exist. The service test named for querying transactions expects filtered results, so test intent and implementation disagree.

Solution: define filter semantics and pass filters from HTTP input. Add a repository query scoped to account owner, direction, and amount range; include pagination and stable sorting so a customer with many transactions does not load the entire ledger.

Test: add fixtures for two customers and several directions/amounts; verify customer isolation, lower and upper boundaries, combinations, empty result, and paging.

P1 · 8. KYC event flow is not active and is not wired

Evidence: @KafkaListener is commented out in CustomerVerificationListener. Its CustomerVerificationService field is never injected. That service's CustomerRepository field is also never injected. The switch has no break: ID falls through to NATIONAL_CODE. Wallet operations never read Customer.isVerified.

Why it matters: Kafka will not call this method as a listener; if called directly, it can hit null dependencies and an ID event can trigger the wrong lookup. Even a successful verification update does not gate wallet operations.

Solution: constructor-inject both dependencies, enable a configured listener with a stable topic/group, use arrow-style switch cases, handle unknown identifiers explicitly, and enforce KYC before financial operations. Make event handling observable and safely retryable.

switch (event.getIdentifierType()) {
    case "ID" -> verificationService.handleByCustomerId(...);
    case "NATIONAL_CODE" -> verificationService.handleByNationalCode(...);
    default -> throw new InvalidIdentifierTypeException(...);
}

Test: test each event type, missing customer, unknown type, and the wallet's rejection of an unverified owner.

P1 · 9. Retry safety and concurrent debits are not solved

Evidence: Transaction.requestId is unique, suggesting idempotency, but the credit request has no request ID and its converter does not set one. No code checks for an existing request before applying it. Debit has no lock/version check around available funds.

Why it matters: if a client times out after a deposit commits and retries, the same deposit could be applied twice. Two withdrawals can both read the same old balance and together overdraw it.

Solution: require an idempotency key for both money-moving requests, store it with a uniqueness constraint, and return the original result on retry. Calculate funds and write the debit atomically using optimistic locking (@Version) or a suitable database lock. Keep the ledger as the authoritative record.

Test: repeat the same request ID and assert only one transaction; run two withdrawals concurrently against limited funds and assert no invalid negative balance.

P1 · 10. Money uses Double and input/error handling is weak

Evidence: commands, entities, and DTOs use Double for amounts. Request fields have no validation annotations. Missing account results can become null dereferences, and there is no consistent exception-to-HTTP error mapping.

Why it matters: binary floating-point cannot exactly represent many decimal fractions, which is undesirable for currency. Invalid amounts and unknown IDs can return confusing server errors.

Solution: use BigDecimal, validate scale and positivity, add Bean Validation such as @NotNull/@Positive, and map domain exceptions to clear 400/404/409 responses with @RestControllerAdvice.

Test: invalid JSON, missing IDs, unsupported account type, zero/negative amount, excess decimal places, and not-found cases should return stable status codes and error bodies.

P2 · 11. NotificationService records a pending message but does not send it

Evidence: NotificationService.send starts CompletableFuture.runAsync, creates a Message with status PENDING, and saves it. There is no provider call or worker that marks it SENT/FAILED.

Why it matters: method name and API response can imply delivery, but only database queuing happens. Async failures do not reach the original request. The write is not in the wallet transaction.

Solution: describe it as enqueueing, not sending. For reliable delivery, persist an outbox/message row in the same database transaction as the wallet operation, then process it with a worker that retries and records outcomes. Do not let a notification failure undo or falsely confirm money movement.

Test: assert the pending event is created transactionally and that worker success/failure updates status with retry behavior.

P2 · 12. Tests do not reliably prove the intended behavior

Evidence: the balance test name mentions a daily limit, but it calls the service directly and tests only a balance calculation. Its fixture has fifteen positive 10,000 transactions, while the service sums all amounts and the test expects 50,000. The history test expects results, but the service returns empty. The controller's static counter is not reset between tests; its concurrency test increments a shared plain integer.

Why it matters: names and assertions do not match the behavior under test. The service tests cannot prove a controller rate limit. Shared mutable state makes tests order-dependent, and an unsynchronized counter can lose updates.

Solution: make one behavior the focus of each test. Reset state or inject a limiter. Use JUnit assertions, deterministic fixtures, and separate service/API/integration tests. Keep tests aligned to documented semantics and update the README only when requirements truly change.

Test plan: for every finding above, add a failing focused test first, implement the smallest fix, then run the whole suite.

P2 · 13. Response and persistence details can surprise clients

Evidence: CreditAccountDTO has private fields and only @AllArgsConstructor, with no getters or @Data. AccountBalanceDTO.number is a Long populated from the database ID, while the account's public number is a UUID string. Account.type has no @Enumerated(EnumType.STRING), so JPA's default is ordinal storage.

Why it matters: default Jackson serialization may not expose private DTO fields without getters/field annotations. API consumers may receive a database ID while expecting an account number. Ordinal enums can become incorrect if enum order changes.

Solution: use a record or explicit getters for response DTOs; name and type fields according to their meaning; add JSON contract tests; persist enum names with @Enumerated(EnumType.STRING).

5. Configuration observations

  • application.yml uses in-memory H2 and ddl-auto: create-drop. Data is lost when the process stops; this is convenient for a sample but not durable storage.
  • Spring cache type is simple, and AppConfig creates an in-memory cache manager. No cache annotations or cache use are visible. Redis dependency/config and a Redis container are present but do not make this cache Redis-backed.
  • Kafka dependency, consumer settings, and Docker Compose broker exist, but the only KYC listener annotation is commented out.
  • All controller operations use POST, including balance and transaction reads. This can be changed to GET if the API contract permits.
  • The servlet context path and controller mapping both include /wallet; document and test the actual external path.

These are lower priority than correctness of money movement, but they matter when explaining what infrastructure is active versus merely configured.

7. How to present this review in an interview

A clear 45-second summary

“The project has a clear Spring layered shape: the controller handles HTTP, commands and queries carry input, WalletService coordinates use cases, and Spring Data repositories persist JPA entities. My highest-priority findings are correctness issues in the money path: account creation attaches an unsaved customer, transaction persistence is not configured safely, debit uses a different identifier contract from credit, and balance adds debits instead of subtracting them. I would confirm the intended API and business rules, add focused failing tests, and fix those before polishing infrastructure.”

If asked what you would fix first

  1. Ask whether the task is account creation, debit, or history, and confirm the expected identifier and ledger semantics.
  2. Write one small test demonstrating the failure. For example: deposit 100, withdraw 30, expected balance 70.
  3. Make a minimal design correction; avoid changing unrelated integrations in the same patch.
  4. Explain how the change handles retries, concurrency, and error cases if money movement is involved.
  5. Run the focused test and then the full suite; report any known limitation plainly.

Useful phrases

  • “I want to verify whether this field is the database ID or the public account number before changing the API.”
  • “This test name says rate limit, but it calls the service directly, so it cannot validate the controller's limiter.”
  • “I would keep the ledger entry and account update in one database transaction, then publish notification work reliably after commit.”
  • “I’m treating the README as the stated requirement and checking whether each rule is enforced in the use case.”
Reviewer mindset: state the evidence, explain the user impact, propose the smallest safe change, and show how a test would prove it.

Review scope: checked-in README, Maven configuration, application YAML, Java production source, test source, the Maven test run, and local HTTP smoke checks. No application code was changed during this review. Priority labels reflect impact if the documented wallet behavior is expected.

Critical findings

[x] 01 fix: persist customers before creating wallet accounts

Problem: A new account referenced a customer that had not been saved, which could make the account save fail. Recreating the same customer could also duplicate owners.

Fix: Look up the customer by national code, save a new customer only if needed, and then save the account. The national code has a unique database constraint.

Interview: “I save or reuse the owner first, so multiple accounts can refer to the same customer.” A separate customer creation use case is another design option.

Commit: 1deec8c. Check: Tests cover creating a customer and reusing an existing one.

[x] 02 fix: persist wallet transactions through the owning relationship

Problem: The account transaction collection was immutable, and saving an account alone did not ensure that its ledger entries were saved.

Fix: Use a mutable list, connect each transaction to the account, and save the transaction explicitly. The transaction owns the relationship and stores the account foreign key.

Interview: “Adding an object to the account's collection is not enough to persist the owning side. I set the account on the transaction and save the transaction.” A list does not prevent duplicates; a unique request ID is enforced in the database when present.

Commit: 685a723 (fix: persist credit and debit transactions). Check: Credit and debit tests verify the saved transaction points to its account.

[x] 03 fix: map debit requests by public account number

Problem: Debit lacked a request converter and used a numeric database ID even though the public account number is a UUID string.

Fix: Convert the debit request to a command, keep the account number as a string, find the account by its public number, and return 404 if it does not exist.

Interview: “I made the request, command and repository lookup agree on the identifier that the client actually receives.”

Commit: 52a766b (fix: map debit requests by account number). Check: Focused service and controller tests cover conversion and a missing account.

[x] 04 fix: calculate balances from transaction direction

Problem: The old balance added withdrawals as if they were deposits. Amounts used Double, and the result used the database ID instead of the public account number.

Fix: Use BigDecimal and a direction enum; query accounts by customer; add credits and subtract debits; return public account numbers. Amounts are limited to the database's precision and two decimal places.

Example: A 100.00 credit followed by a 30.00 debit produces 70.00. Decimal amounts such as 0.10 and 0.20 are calculated exactly.

Commit: cb86397 (fix: calculate wallet balances using transaction direction). Check: Focused tests cover mixed directions, decimal amounts and the public account number.

[x] 05 fix: require customer verification for transactions

Problem: The README requires a verified customer before a transaction, but the service did not check the verification flag.

Fix: Before credit or debit, load the account and reject an unverified or missing owner with 403. An unknown account returns 404. Successful operations continue for verified customers.

Interview: “I apply the README rule in the service before saving a ledger entry. This checks the flag; the separate KYC event flow still needs work.”

Commit: 3c10015. Check: Focused tests cover both rejected transactions and successful operations for verified owners.

[x] 06 fix: prevent withdrawals from savings accounts

Problem: The README allows only deposits for savings accounts, but the debit method did not check the account type.

Fix: Reject a debit unless the type is CHECKING. Savings accounts can still be credited. The code uses SAVING; the README says SAVINGS.

if (account.getType() != AccountType.CHECKING) {
    throw new ResponseStatusException(HttpStatus.BAD_REQUEST,
            "Only checking accounts can be debited");
}

Commit: 9f97ada (fix: don't access withdrawals from savings accounts). Check: Three focused tests passed: savings debit is rejected, checking debit is accepted, and savings credit is accepted.

[ ] 07 fix: reject nonpositive transaction amounts

Problem: The current precision check does not reject zero or negative values. A negative deposit or withdrawal can change the ledger in an unexpected direction.

Proposed fix: Require amounts greater than zero for both credit and debit using amount.compareTo(BigDecimal.ZERO) > 0. Return a clear client error before saving.

Check: Test zero and negative amounts for both operations, and verify no ledger entry or notification is created.

[ ] 08 fix: reject withdrawals exceeding the account balance

Problem: A checking account can currently be debited without checking available funds. For example, a withdrawal of 120 from a balance of 100 can be recorded.

Proposed fix: Calculate the balance from the ledger and reject a debit greater than the balance; allow a debit equal to it.

Check and limitation: Test sufficient, exact and insufficient balances. A separate concurrency fix in item 10 is needed to make this check safe when requests arrive together.

[ ] 09 fix: authorize account ownership

Problem: The project accepts account and customer identifiers without establishing that the caller owns them. A verified account owner is not proof of the caller's identity.

Proposed fix: Choose an authentication provider and caller identity model, then compare the authenticated customer to the account owner before accessing it. Apply the same principle to customer-scoped queries.

Check: An authenticated owner succeeds; another customer is denied. This depends on selecting an identity integration.

[ ] 10 fix: make wallet writes idempotent and concurrency-safe

Problem: A retry can create another transaction, and simultaneous withdrawals can both observe the same balance. The unique request ID alone does not return a prior result; the credit request does not currently supply one.

Proposed fix: Require and persist request IDs for credit and debit, return the prior result for an identical retry, and serialize each balance check and write using a suitable database lock or version strategy.

Check: Retry the same request and assert one ledger entry; race two debits against limited funds and assert the balance cannot be overdrawn.

[ ] 11 fix: enforce the five-per-day balance inquiry limit

Problem: The controller uses a static map, permits a sixth request, has no daily reset and is not safe for concurrent requests.

Proposed fix: Define the time zone and day boundary, then atomically count requests per customer and day. A shared store is required if multiple application instances must share the limit.

Check: The fifth request succeeds, the sixth is rejected, the next day resets, customers are isolated, and concurrent calls respect the limit.

[ ] 12 feat: return filtered customer transaction history

Problem: The transaction history method is a stub and returns an empty list.

Proposed fix: Filter by customer, direction and amount, and provide stable ordering and pagination. Query only the relevant customer's data.

Check: Cover different customers, directions, boundaries, combinations and empty pages. Five deposits of 10,000 with a minimum of 6,000 total 50,000; the existing 75,000 test expectation needs correction.

[ ] 13 fix: connect KYC events to transaction eligibility

Problem: The Kafka listener annotation is disabled, dependencies are not injected, and event dispatch can fall through between identifier types. The service now checks verification, but the event flow that updates it is incomplete.

Proposed fix: Inject the listener and service dependencies, enable a configured listener, dispatch each identifier correctly, and handle missing customers and failures clearly.

Check: Exercise customer ID and national code events and show that verification changes transaction eligibility.

Follow-up risks also listed in the review

[ ] 14 fix: persist notification work reliably

Problem: Notification work runs asynchronously and records a pending message; failure and delivery are not reliably tied to the wallet transaction.

Proposed fix: Persist notification work with the wallet change using an outbox or similar durable approach, then process it with retries and observable status.

Check: Cover successful delivery, failures, retries and the relationship between the ledger commit and queued message.

[ ] 15 fix: expose credit response fields to JSON

Problem: CreditAccountDTO has private fields and a constructor but no getters, which can prevent the expected response fields from being serialized.

Proposed fix: Add accessors or use a response record, then verify the actual JSON contract.

Check: Assert that a successful credit response contains the account number and amount.

[ ] 16 chore: configure durable database storage and schema migrations

Problem: The current configuration uses in-memory H2 and create-drop, so application data is not durable across restarts.

Proposed fix: Choose a durable database for deployment, use environment-specific configuration, and manage schema changes through migrations.

Check: Restart the application and verify saved data survives; apply migrations to a fresh and an existing database.

[ ] 17 chore: align Redis configuration with the cache implementation

Problem: Redis settings and dependencies exist, but the configured cache is in memory. Their presence can create an incorrect impression that Redis backs the cache.

Proposed fix: Decide whether Redis is needed. Configure and use it deliberately or remove the unused settings and dependencies.

Check: Verify the cache provider and expected behavior against the chosen configuration.

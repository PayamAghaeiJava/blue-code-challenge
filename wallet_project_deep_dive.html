How to read this guide
This guide separates what the project is trying to do from what the checked-in code currently does. That distinction matters: several business rules are described in the README but are not fully implemented.

Repository: Java 21 · Spring Boot 3.3.3 · Maven · source reviewed from this checkout

1. The project in two minutes

This repository is a sample backend for a bank wallet. It models customers, accounts, and transactions, exposes HTTP endpoints for opening an account and moving or reading money, and includes early scaffolding for customer identity verification (KYC) and notifications.

The code is organized in layers. The REST controller receives HTTP requests. It converts request-shaped objects into application commands or queries. WalletService contains most wallet behavior and calls Spring Data repositories. JPA entities represent database rows and their relationships. Spring Boot starts the application and reads configuration from YAML.

HTTP client → WalletController → request converter → WalletService → JPA repository → H2 database
                                                     ↘ notification / KYC scaffolding
Important snapshot: this is an interview sample or work-in-progress, not a complete production wallet. The README describes intended rules, but account creation, transaction persistence, balance arithmetic, KYC enforcement, transaction search, and the daily limit all have implementation gaps described below.

2. Business model and promised rules

The README states these requirements:

  • A customer may own several accounts; each account has one owner.
  • Account kinds are savings and checking. Savings should allow deposits only; checking should allow deposits and withdrawals.
  • An account can have many transactions. A transaction is a deposit or withdrawal.
  • A customer must pass KYC before transacting.
  • A customer may read the full account balance five times per day.

In the code, Customer, Account, and Transaction are JPA entities. Their intended relationships are:

Customer 1 ───── many Account 1 ───── many Transaction

AbstractEntity supplies a generated Long id to the entities that extend it. Lombok's @Data creates getters, setters, equals, hashCode, and toString at compile time. Those generated methods are convenient for simple DTOs, but using them on JPA entities with bidirectional relationships deserves care because printing or comparing entities can walk relationships unexpectedly.

4. Architecture and useful patterns

Layered application

The controller is the HTTP boundary. It should translate protocol details into application inputs and translate results into HTTP responses. The service is the use-case layer: create an account, credit an account, debit an account, or calculate balances. Repositories hide database access behind interfaces. The entities describe persisted domain data.

Request objects, commands, queries, and DTOs

A request object describes the incoming JSON shape, such as CreateAccountRequest. A command describes an action the application should perform, such as CreateAccountCommand. A query describes information to retrieve, such as AccountBalanceQuery. A DTO is a response-shaped object sent back to the caller. Keeping these types separate can protect internal code from HTTP-specific details, though the current project has some mismatches between them.

Converters and dependency injection

CreateAccountRequestConverter and CreaditAccountRequestConverter implement Spring's Converter<S,T> interface. Spring discovers them as components; the controller asks ConversionService to transform request objects to commands. This keeps field mapping outside the controller method. The credit converter's class name contains a spelling error, and it currently does not map a request ID.

Repositories and ORM relationships

AccountRepository and CustomerRepository extend Spring Data JPA's JpaRepository. Spring supplies common methods such as save, findAll, and findById; method names such as findByNumber or findByNationalCode are parsed into queries.

JPA relationships have an owning side. Here, Transaction.account is the owning side because it holds the foreign key; Account.transactions is marked mappedBy = "account", so it is the inverse side. Merely adding a transaction to the account's collection and saving the account does not automatically persist that transaction: there is no cascade configured and no transaction repository is used.

Transactions and asynchronous work

@Transactional on credit/debit asks Spring to wrap each method's database work in a transaction. That helps make related database writes atomic, but it does not repair missing cascade configuration or the immutable collection problem. NotificationService uses CompletableFuture.runAsync, which schedules work on the default async pool. That task is not part of the caller's database transaction and only saves a pending message; it does not send an SMS.

Commands are not automatically CQRS

The project uses command and query class names, which resembles the vocabulary of CQRS (separating writes from reads). It remains a single Spring application with one service and shared repositories; there is no separate read store, event-sourced model, or independent command/query pipeline.

5. HTTP endpoints and request flow

The controller has @RequestMapping("/wallet"). YAML also sets the servlet context path to /wallet/. These prefixes may combine, so the configured application route is likely under /wallet/wallet. Confirm the actual URL against the running server; the tests address /wallet/... directly and may not exercise the configured external context path.

The request bodies are plain Java objects with Lombok-generated accessors. They have no Bean Validation annotations, so amount, IDs, names, and account type are not formally validated at the HTTP boundary.

6. Follow the main use cases

A. Create an account

  1. Spring MVC deserializes JSON into CreateAccountRequest.
  2. The controller asks the conversion service for a CreateAccountCommand.
  3. WalletService.createAccount creates a new Account and a new Customer, copies customer details, attaches the customer as owner, sets the type, and assigns a UUID string.
  4. It calls accountRepository.save(account) and returns the account number.
The customer is never saved through CustomerRepository, and the owner relationship has no cascade = PERSIST. JPA normally rejects saving an account that references a transient, unsaved customer. Account type is also parsed with AccountType.valueOf, so the accepted value must match the enum spelling exactly; the enum says SAVING, while the README says SAVINGS.

B. Credit (deposit)

The service finds an account using the public string number. It creates a Transaction whose direction is the literal "credit", adds it to account.getTransactions(), schedules a notification, saves the account, and returns a small DTO.

There are three major complications. First, the create path sets transactions to Set.of(), an immutable set, so adding the first transaction throws UnsupportedOperationException. Second, the transaction collection is the inverse side of the JPA relation and no cascade is configured, so a mutable collection alone would still not guarantee the transaction gets stored. Third, CreditAccountRequest has no request ID, so the unique transaction key cannot provide idempotency for this endpoint.

C. Debit (withdrawal)

The debit endpoint receives an account number typed as Long, but the account's public number is a UUID-like String. The service then calls findById, which searches the database primary key, not the public account number. A valid public account number therefore cannot be represented by this request shape. The code also does not check account type, customer KYC status, sufficient funds, positive amount, or ownership of a request.

D. Balance inquiry

The controller uses a static map keyed by customer ID. The service loads all accounts, selects accounts whose owner's database ID matches, sums transaction amounts, and returns account ID plus amount. This is simple to read, but loads the whole account table and uses an unfiltered sum. Since both credit and debit amounts are added as positive values, the calculated result is a gross movement total, not a net wallet balance.

E. Transaction list

The query object has fields for customer, lower amount, upper amount, and direction. These fields suggest intended filters. No repository query or filtering code exists yet; the service returns Collections.emptyList(). The controller only sets customer ID, so even a future implementation would need a way to receive the other filters.

7. KYC and notifications

KYC verification scaffold

CustomerVerificationService can look up a customer by database ID or national code, set the verified flag, and save it. The ID path throws a generic runtime exception when no customer exists. The national-code path dereferences the result without checking for null. Its repository field is not injected, so normal Spring-created instances would have a null repository.

CustomerVerificationListener contains an event class and handler for identifiers of type ID or NATIONAL_CODE. The @KafkaListener annotation is commented out, and the verification service field is also not injected. The switch cases have no break or arrow syntax: an ID event falls through into the national-code handler. Exceptions are caught and logged, which can hide a failed event from the caller unless monitoring looks at those logs.

Most importantly, wallet credit/debit does not check Customer.isVerified. The README's KYC-before-transactions rule is not enforced by the current transaction use cases.

Notification scaffold

NotificationService.send asynchronously builds a Message with status PENDING and saves it. There is no SMS provider or consumer that marks it sent or failed. The throws RuntimeException declaration does not report exceptions from the separate asynchronous task to the original caller.

9. Tests: what they cover and what they do not

WalletServiceTest uses Spring's test context and Mockito mocks for repositories and notifications. One test constructs transactions and expects a balance of 50,000, but it does not test the five-per-day limit despite its name. A second test sets up customer and amount/direction data and expects filtered transaction results, while the implementation currently returns an empty list; as written, that expectation appears inconsistent with the service.

WalletControllerTest uses MockMvc to send balance requests. It aims to check five allowed calls, a sixth rejected call, different customers, and concurrent calls. The production counter is static, never reset per test/day, and implemented with a non-thread-safe HashMap; the concurrency test also updates a shared integer without synchronization. Test execution order can affect cases that reuse the same customer ID.

Good review habit: distinguish test intention from test evidence. Read the assertion, check whether setup isolates state, and compare the expected behavior with the exact implementation. A passing test suite alone cannot prove a business rule when the test does not exercise that rule.

11. How to talk through this in an interview

A clear opening summary could be:

“This is a Java 21 Spring Boot wallet API organized into a REST adapter, an application service, and JPA entities/repositories. It models customer → account → transaction, with additional KYC and notification scaffolding. I would first clarify whether we are discussing intended requirements or the current implementation, because several stated rules are not enforced yet.”

When asked to review or change code:

  1. Restate the expected behavior and ask about ambiguous details: account identifier, debit representation, transaction direction, KYC failure behavior, and the exact daily window.
  2. Trace one request end to end: controller input → conversion → service → repository/entity → response.
  3. Identify the smallest correctness issue with concrete evidence. For example, saving an account whose owner is an unsaved customer or adding to Set.of().
  4. Say how you would test it: a focused service test for successful persistence and invalid paths, plus an API test for request/response mapping.
  5. Implement in small steps, narrating trade-offs. For money, mention decimal representation; for retries, explain idempotency; for rate limits, explain concurrency and shared state.

A sensible first-change order is: make account creation and transaction persistence correct; align public identifiers; enforce and test wallet rules; implement transaction search; then improve rate limiting, validation, errors, and integration infrastructure.

12. Run and explore the project

From the repository root on Windows, the Maven wrapper commands are:

.\mvnw.cmd spring-boot:run   # start the app
.\mvnw.cmd test               # compile and run the JUnit tests
.\mvnw.cmd clean package     # clean and create the packaged application

Use a Java 21 JDK. The configured database is in-memory H2. The server port is 8080. The URL path includes the context path and controller mapping described earlier. Optional containers are declared in dc.yml and can be started with docker compose -f dc.yml up -d; stop them with docker compose -f dc.yml down.

Commands are documented from project configuration and were not run while preparing this guide. The source is a snapshot; check current runtime behavior before relying on an endpoint or infrastructure integration.

How to use this guide

For each issue, explain what was wrong, show your fix, and talk about the test and any limits.

Test status
Items 01–10 have commits. Item 10 needs a new test run after the code was simplified. Item 11 is not committed yet; its tests and Kafka flow still need to be checked.
01

Save the customer first

Problem: An account needs an owner, but the customer might not be saved yet.

Solution: Look for the customer by national code. If the customer exists, use it. If not, save a new customer, then create the account.

Tests: We check creating an account for a new customer and for an existing customer.

Tradeoff: One method now creates both customers and accounts. Another option is to create customers in a separate method. Two requests creating the same customer at once can hit the database uniqueness rule.

Say: “I make sure the customer is saved before creating the account, and I reuse existing customers.”
02

Save the transaction

Problem: Adding a transaction to the account’s list did not make sure it was saved in the database.

Solution: Set the transaction’s account, then save the transaction using its repository.

Tests: Service tests check that credit and debit save a transaction with the correct account. These tests use mocks.

Tradeoff: A List does not stop duplicates by itself. A Set depends on equals and hashCode, so database rules are still needed.

Say: “The transaction holds the account link, so I set that link and save the transaction.”
03

Use the account number for withdrawals

Problem: The debit request did not correctly pass the public account number through the code.

Solution: Copy the number into the command, find the account by that number, and return 404 if the account is missing.

Tests: Tests check request conversion, account lookup, and the 404 response.

Tradeoff: Knowing an account number does not prove the caller owns the account. That needs a separate security check.

Say: “I use the public account number from the request and return 404 when the account does not exist.”
04

Calculate the correct balance

Problem: The balance did not properly separate deposits from withdrawals. Double can also give small rounding errors with money.

Solution: Use BigDecimal for money. Add credits and subtract debits. Load accounts for the requested customer.

Tests: Tests check credits, debits, decimal amounts, and returned account numbers.

Tradeoff: BigDecimal needs care with decimal places. Adding up every transaction may become slow when there are many.

Say: “I use BigDecimal for money, add deposits, and subtract withdrawals.”
05

Check customer verification

Problem: The README says a customer must be verified before making a transaction.

Solution: Before credit or debit, check the account owner’s verification flag. Return 403 if the owner is not verified.

Tests: A service test checks that both operations are rejected and nothing is saved or sent.

Tradeoff: This only checks the saved flag. Another process must update it. Verification also does not prove who is calling the API.

Say: “I check the customer’s verification status before every deposit and withdrawal.”
06

Stop savings withdrawals

Problem: The README says a savings account can receive deposits but cannot make withdrawals.

Solution: Allow a debit only when the account type is CHECKING.

Tests: Tests cover a rejected savings withdrawal, a checking withdrawal, and a savings deposit.

Tradeoff: This check is simple. If more account types are added, their rules may need a separate place.

Say: “I check the account type and reject withdrawals from savings accounts.”
07

Require a positive amount

Problem: A zero or negative amount could create an incorrect transaction.

Solution: Reject amounts that are zero or less for both deposits and withdrawals.

Tests: Tests check zero and negative amounts for both operations. They also check that nothing is saved or sent.

Tradeoff: If reversals are needed later, they should have their own clear design.

Say: “I check that every deposit and withdrawal has an amount greater than zero.”
08

Check the balance before withdrawal

Problem: A customer could withdraw more money than the account had.

Solution: Calculate the balance before saving. Reject the withdrawal if the amount is greater than the balance.

Tests: Tests cover an empty account, too little money, enough money, and withdrawing the exact balance.

Tradeoff: This check alone cannot protect against two withdrawals at the same time. Item 09 handles that.

Say: “I check the balance before saving and reject withdrawals that are too large.”
09

Handle withdrawals at the same time

Problem: If an account has 100, two withdrawals of 80 could both see 100 and both succeed.

Solution: Use PESSIMISTIC_WRITE to lock the account while a transaction is running. A second request waits, then checks the updated balance.

Tests: An H2 database test starts two withdrawals of 80 from a balance of 100. One succeeds and one is rejected.

Tradeoff: Requests for the same account may need to wait. Every part of the code that changes transactions must use the same locking rule. The production database needs its own check.

Say: “I lock the account so two requests cannot check and change its balance at the same time.”
10

Allow five balance requests per day

Problem: The old counter allowed a sixth request, did not reset each day, and could fail with simultaneous requests.

Solution: Count requests for each customer. Allow five, return 429 for the sixth, and reset the counts at midnight UTC. Use synchronized to protect the count.

Tests: Tests cover the limit, different customers, the new day, and simultaneous requests. The earlier version passed; the current simpler version needs a new test run.

Tradeoff: Counts are kept in memory. Restarting clears them, and different application instances do not share them. A shared store could solve this.

Say: “I allow five balance checks per customer each day and reset the count at midnight UTC.”
11

Connect KYC events

Problem: The Kafka listener was disabled, its required services were missing, and an ID event could also run the national-code case.

Solution: Enable the listener, provide its services, check incoming JSON, choose the correct identifier, and update the customer’s verification flag.

Tests: The code compiled. The event logic and a real Kafka connection still need tests. The change is not committed yet.

Tradeoff: The team needs to agree on the topic and JSON format. Error handling and failed messages also need a production plan.

Say: “I connected the KYC listener to the customer service. Next I would test both identifier types and confirm the message format.”

Explain what you tested, and be clear about what still needs testing.

Critical Wallet
Code Issues

What can fail, why it matters, and how to repair it safely.

Review scope
Core account, transaction, balance, KYC, and rate-limit paths in this Java Spring Boot repository. Findings combine source review with the recorded Maven test run and local HTTP smoke checks.

Prepared November 20, 2026 · Project: Java 21 / Spring Boot 3.3.3

Executive summary

This project has a sensible starting structure: an HTTP controller delegates to an application service, which uses Spring Data repositories and JPA entities. The highest-risk gaps are in the money-moving path: account creation fails, debit does not have a usable API mapping, transactions are not safely persisted, and balance arithmetic counts withdrawals like deposits.

          Balance + history

The first fixes I’d prioritize are the ones that can stop account creation, break debits, or report the wrong balance. I verified several of these with the project’s tests and a local HTTP run.”

P0 · 1 Account creation fails at persistence

Where: WalletService.createAccount() and Account.owner.

The service creates a new Customer, attaches it to a new Account, and saves only the account. The owner relationship has no cascade = PERSIST, and the customer repository is not used. The database therefore receives an account that references a transient, unsaved customer. The valid-shaped create request returned HTTP 500 in the smoke run.

Impact: the API cannot reliably create the accounts required by every later wallet operation. The code also creates a new customer for each account instead of reusing an existing customer who may own multiple accounts.
Repair: define customer identity and lifecycle. Find the customer by national code or save a new customer first; then attach that persisted customer to the account. Make national code unique if it is the identity key, and wrap the use case in a database transaction.
@Transactional
public String createAccount(CreateAccountCommand command) {
    Customer owner = customerRepository.findByNationalCode(command.getNationalCode())
        .orElseGet(() -> customerRepository.save(newCustomer(command)));
    Account account = new Account();
    account.setOwner(owner);
    return accountRepository.save(account).getNumber();
}

Prove the fix: create two accounts for the same national code. Assert that both accounts point to one customer row and that each account can be loaded after the transaction commits.

P0 · 2 Transaction entries are not safely stored

Where: WalletService.createAccount(), creditAccount(), debitAccount(), and Account.transactions.

Creation initializes transactions with Set.of(), which cannot be changed. Credit/debit later call add(). In addition, the collection is the inverse side of the JPA relationship (mappedBy = "account"), has no cascade, and no transaction repository is used. The transaction's account field owns the database foreign key.

Impact: mutation can throw UnsupportedOperationException; even with a mutable set, saving the account does not necessarily persist the new ledger row. Without a durable transaction record, the wallet cannot reconstruct balance or audit money movement.
Repair: use a mutable collection when the in-memory relationship needs one. Persist transaction rows explicitly through a TransactionRepository, or configure intentional cascade and maintain both sides with entity helper methods. Always set the owning Transaction.account side.
Transaction tx = new Transaction(requestId, account, Direction.CREDIT, amount);
transactionRepository.save(tx); // transaction owns account_id

Prove the fix: credit and debit a persisted account, commit, clear the persistence context, reload the transactions, and verify their account IDs and request IDs.

P0 · 3 Debit cannot reliably identify an account

Where: WalletController.debitAccount(), debit request/command, and WalletService.debitAccount().

The controller asks Spring's ConversionService to convert DebitAccountRequest to DebitAccountCommand, but no converter for those classes exists. Both types declare a numeric account number, and the service calls findById(). The public account number generated by Account is a UUID string. Credit uses that public number through findByNumber(). A valid-shaped debit returned HTTP 500 in the smoke run.

Impact: the API contract is inconsistent. A caller cannot reliably send the same account identifier for credit and debit, and the missing conversion may prevent the service from running at all.
Repair: choose one external identifier. If it is the UUID account number, make the debit request and command fields strings, add a converter that copies request ID, account number, and amount, and use findByNumber(). Return a 404 domain response when absent.
Account account = accountRepository.findByNumber(command.getAccountNumber())
    .orElseThrow(() -> new AccountNotFoundException(command.getAccountNumber()));

Prove the fix: test a debit using a real UUID account number, an unknown UUID (404), and invalid JSON (400). Assert that no database primary key is confused with the public account number.

P0 · 4 Balance is calculated incorrectly

Where: WalletService.accountBalance().

The method sums every transaction amount without reading its direction. The test fixture contains 10 deposits and 5 withdrawals of 10,000 each. Its expected net balance is 50,000, but the service adds all 15 and returns 150,000. The test failure confirms the error.

Impact: users may see money that is not available. Balance is a central financial result, so this is a correctness blocker.
Repair: model money with BigDecimal and direction with an enum. Define the balance as the sum of credits minus the sum of debits. Do not store or expose an ambiguous amount without a currency/scale policy. Query only the target customer's accounts instead of loading every account.
// After adopting BigDecimal and a Direction enum
BigDecimal balance = transactions.stream()
    .map(tx -> tx.getDirection() == Direction.CREDIT
        ? tx.getAmount() : tx.getAmount().negate())
    .reduce(BigDecimal.ZERO, BigDecimal::add);

Prove the fix: deposit 100, deposit 50, withdraw 30; expect 120. Also test decimal fractions, no transactions, and more than one account.

P1 · 5 Required transaction controls are missing

Where: README business rules compared with WalletService.creditAccount() and debitAccount().

The README says customers must pass KYC, savings accounts allow deposits only, and checking accounts allow deposits and withdrawals. The write methods do not check verification or account type. Debit also does not reject zero/negative amounts or insufficient funds. No authentication or account-ownership check is visible in this project.

Impact: a caller can attempt operations that violate the stated product rules. If these endpoints are exposed to untrusted users, accepting caller-supplied customer/account IDs without proving ownership is an access-control risk.
Repair: enforce these rules in the service/use case so every entry point shares them. Identify the caller from authentication, verify ownership, require a verified customer, enforce account type and positive amount, and check available funds atomically before recording a debit. Align the README's SAVINGS spelling with the enum's SAVING.

Prove the fix: test valid checking debit, savings debit rejection, unverified customer, another user's account, zero/negative amount, and insufficient funds.

P1 · 6 Retries and simultaneous debits can corrupt results

Where: transaction requestId, credit request/converter, and account debit flow.

Transaction.requestId is unique, suggesting retry protection, but the credit request has no request ID and the converter cannot populate one. The service does not look for an earlier transaction before applying an operation. There is also no lock/version check around balance validation and debit recording.

Impact: a client retry after a timeout can apply the same deposit twice. Two simultaneous debits can both observe the same starting funds and both succeed.
Repair: require an idempotency key for every money-changing request; store it with a uniqueness constraint and return the original result for a retry. Make available-funds checking and debit recording atomic using optimistic locking (@Version) or a suitable database lock. Keep the ledger as the source of truth.

Prove the fix: send the same request twice and assert one ledger entry. Run two concurrent withdrawals whose total exceeds the balance and assert exactly one is rejected.

P1 · 7 Balance limit is not five per day

Where: WalletController.requestCounter and accountBalance().

The static HashMap blocks only when the current count is greater than five. In a fresh app, requests one through six returned 200; request seven returned 429. There is no daily reset or expiration. The test suite also reuses customer ID 12345; static state leaks across tests, making a test that expects 200 receive 429.

Impact: behavior contradicts the five-per-day requirement and changes after application restart. Concurrent map/check/update operations are not atomic. A concurrent test passed once, but does not prove safety.
Repair: define the daily time zone and reset boundary. Use an atomic counter keyed by customer and date, with expiration. For multiple application instances, use an atomic shared limiter such as Redis. Keep this separate from cache configuration.

Prove the fix: fifth call 200; sixth 429; next day's first call 200; independent customer counters; a simultaneous burst allows exactly five. Inject a clock so reset tests are deterministic.

P1 · 8 Transaction history is an empty stub

Where: WalletService.listTransactions().

The service has a TODO and returns Collections.emptyList(). Runtime returned HTTP 200 with []. The service test expected a non-empty filtered sum of 75,000 but received 0.

Impact: clients cannot see transaction history, and the successful HTTP status can disguise the missing feature.
Repair: define the query filters, expose them in the endpoint, and add a repository query scoped to customer-owned accounts with direction and amount bounds. Add pagination and deterministic ordering so large histories remain efficient.

Prove the fix: include two customers, several directions and amounts, boundary values, no matches, and multiple pages. Verify a customer never sees another customer's transactions.

P1 · 9 KYC processing is disconnected from wallet operations

Where: CustomerVerificationListener, CustomerVerificationService, and wallet credit/debit service methods.

The Kafka listener annotation is commented out. The listener's service field is not injected; the verification service's repository field is not injected. The switch has no break, so an ID event falls through into the national-code handler. Credit/debit do not check the customer's verified flag.

Impact: KYC messages do not update customer state through Kafka, and even a manual update does not prevent an unverified customer from transacting.
Repair: use constructor injection, enable a configured listener, dispatch identifier types without fall-through, handle missing customers and unknown types explicitly, and enforce verification in wallet use cases. Make event processing observable and safe to retry.
switch (event.getIdentifierType()) {
    case "ID" -> verificationService.handleByCustomerId(...);
    case "NATIONAL_CODE" -> verificationService.handleByNationalCode(...);
    default -> throw new InvalidIdentifierTypeException(...);
}

Prove the fix: test each event route and verify that an unverified customer receives a clear rejection from credit/debit.

Repair sequence for a pair-programming task

  1. Clarify: confirm the public account identifier, expected balance semantics, KYC behavior, and daily-limit boundary.
  2. Write a failing test: choose one behavior, such as a 100 deposit and 30 withdrawal producing balance 70.
  3. Repair the smallest slice: align request mapping, service rule, repository persistence, and response.
  4. Check the boundary cases: unknown account, retry, invalid amount, concurrent debit, and authorization.
  5. Report precisely: say what passed and what remains unverified.

Follow-up risks after the critical fixes

  • NotificationService only saves a PENDING message asynchronously; it does not deliver SMS or report delivery status. Consider a transactional outbox and worker.
  • CreditAccountDTO has private fields with an all-args constructor but no getters; add a JSON serialization test and a record/getters.
  • H2 is in-memory with ddl-auto: create-drop; data disappears at shutdown. Use durable storage and migrations for deployment.
  • Redis/cache configuration is simple in-memory cache; the Redis starter is present but not used as the cache backend here.
Closing line for the presentation: “The architecture is understandable, but the wallet's core correctness needs attention before feature polish. I would first make account creation and ledger persistence reliable, then align the debit contract and balance math, and prove each change with focused tests.”

How the Pieces Fit
in This Codebase

A step-by-step guide to the request, application, persistence, and response flow, with examples from the actual Java classes.

One sentence: the web layer receives input, the application service performs a use case, Spring Data repositories talk to JPA entities, and the controller returns a result. KYC and notifications are separate supporting flows, and both are incomplete in this snapshot.

Project: Java 21 · Spring Boot 3.3.3 · Spring MVC · Spring Data JPA · H2

2. Start at the HTTP boundary: WalletController

WalletController is annotated with @RestController, so Spring MVC exposes its methods as HTTP endpoints and handles JSON request bodies. Its class mapping is /wallet. Methods use @PostMapping for create, credit, debit, balance, and transactions.

@RestController
@RequestMapping("/wallet")
public class WalletController {
    @PostMapping("/create")
    public ResponseEntity<?> createAccount(
            @RequestBody CreateAccountRequest request) {
        CreateAccountCommand command =
                conversionService.convert(request, CreateAccountCommand.class);
        return ResponseEntity.ok(walletService.createAccount(command));
    }
}

Here Spring turns the request JSON into a Java request object. The controller then hands off the work to the service and wraps the returned value in an HTTP 200 response.

Example JSON shape for account creation:

{
  "nationalCode": "0012345678",
  "firstName": "Sara",
  "lastName": "Example",
  "mobile": "09120000000",
  "type": "CHECKING"
}

This is the request shape, not a guarantee that creation succeeds. The service currently builds a new owner but does not save that customer or configure cascading persistence.

URL detail: WalletController contributes /wallet, and application.yml sets the server context path to /wallet/. Together they may make the external URL /wallet/wallet/create. The controller tests call /wallet/... through MockMvc, so verify the exact deployed URL in a running app.

3. Converters: translating web input into application input

A request object belongs to the web boundary. A command or query belongs to the application's use-case boundary. The converter copies fields between these types.

@Component
public class CreateAccountRequestConverter
        implements Converter<CreateAccountRequest, CreateAccountCommand> {
    @Override
    public CreateAccountCommand convert(CreateAccountRequest source) {
        CreateAccountCommand command = new CreateAccountCommand();
        command.setNationalCode(source.getNationalCode());
        command.setType(source.getType());
        command.setFirstName(source.getFirstName());
        command.setLastName(source.getLastName());
        command.setMobile(source.getMobile());
        return command;
    }
}

@Component lets Spring discover the converter. The controller uses Spring's ConversionService to locate the matching converter. This keeps field-copying code out of the endpoint method.

Credit uses CreaditAccountRequestConverter (the class name has a typo). It copies account number and amount into CreditAccountCommand, but the request has no requestId, so that value never reaches the service.

Debit difference: the controller calls conversionService.convert(request, DebitAccountCommand.class), but there is no converter from DebitAccountRequest to DebitAccountCommand in the repository. That conversion is likely to fail at runtime until a converter is added or the controller maps the fields directly.

4. Commands and queries: plain input containers

These classes are not controllers and usually do not perform work. They carry typed values to the service:

// command: asks the application to do something
public class CreditAccountCommand {
    private String requestId;
    private String accountNumber;
    private Double amount;
}

// query: asks the application to return information
public class AccountBalanceQuery {
    Long customerId;
}

A command represents a change, such as creating, crediting, or debiting an account. A query represents a read, such as getting a customer's balance. The project uses this vocabulary, but it is still one application service and one database; it is not a separate CQRS system.

Balance is an example where the controller creates the query itself:

AccountBalanceQuery query = new AccountBalanceQuery();
query.setCustomerId(Long.valueOf(customerId));
return ResponseEntity.ok(walletService.accountBalance(query));

5. WalletService: where a use case is coordinated

WalletService is marked @Service. It receives an AccountRepository and a NotificationService through Lombok's @AllArgsConstructor constructor. The controller does not write database code itself; it delegates to this service.

A simplified view of crediting is:

Account account = accountRepository.findByNumber(command.getAccountNumber());
Transaction transaction = new Transaction(
        command.getRequestId(), account, "credit", command.getAmount());
account.getTransactions().add(transaction);
notificationService.send(account.getOwner().getMobile(), "deposit ...");
accountRepository.save(account);
return new CreditAccountDTO(account.getNumber(), transaction.getAmount());

This shows the service coordinating lookup, transaction construction, notification request, save, and result. @Transactional on credit/debit asks Spring to run the method's database operations inside a transaction.

Current behavior caveat: account creation sets transactions to Set.of(), an immutable set. Calling add can throw. Also, Account.transactions is the inverse side of the JPA relationship and has no cascade configured; saving the account alone does not necessarily save a new transaction.

6. Repository and entity: how persistence is represented

AccountRepository extends JpaRepository<Account, Long>. Spring Data implements common methods and derives custom queries from method names:

public interface AccountRepository extends JpaRepository<Account, Long> {
    Account findByNumber(String number);
}

findByNumber searches the account's public number field. findById searches the inherited database primary key. They are different identifiers.

Account and Transaction show the data relationship:

// Account.java
@OneToMany(mappedBy = "account")
private Set<Transaction> transactions;

// Transaction.java
@ManyToOne(optional = false)
@JoinColumn(name = "account_id")
private Account account;

The foreign key lives on Transaction.account. That makes this the owning side. mappedBy = "account" says the account's collection mirrors the relationship field; it does not own the database foreign key. The account's owner is another relationship: @ManyToOne to Customer.

Identifier mismatch in debit: the credit path uses findByNumber(String), while debit calls findById(Long). The account number generated in this project is a UUID string, so debit's Long accountNumber does not match that public identifier.

7. Response DTO: the way data leaves a use case

After the service finishes, it returns a response object or value. The controller passes that value to Spring MVC, which serializes it into an HTTP response.

return new DebitAccountDTO(account.getNumber(), command.getAmount());

DebitAccountDTO has an account field and amount. AccountBalanceDTO has account number and amount. A DTO lets the API return only selected fields instead of exposing a full JPA entity and its relationships.

For balance, the service creates one DTO per matching account, sets the account's database ID into number, and computes an amount. The property name and value are slightly misleading: callers might expect the public UUID number, but the value is actually the database ID.

8. Three request paths, step by step

Path A — create account

  1. JSON is deserialized into CreateAccountRequest.
  2. CreateAccountRequestConverter maps it to CreateAccountCommand.
  3. WalletController calls WalletService.createAccount.
  4. The service creates Account and Customer objects, attaches the Customer, saves only Account, and returns a UUID string.
  5. The controller returns that string with HTTP 200 if saving succeeds.

The visible persistence concern is that the new Customer is transient and the relationship has no persist cascade. A robust implementation should decide whether to find/create and save a customer, then attach the persisted entity.

Path B — credit account

  1. JSON becomes CreditAccountRequest.
  2. The credit converter maps account number and amount into CreditAccountCommand.
  3. The service looks up the account by public number and constructs a credit transaction.
  4. The service requests a notification and saves the account.
  5. The service returns CreditAccountDTO; the controller wraps it in HTTP 200.

The request has no request ID, so the transaction's unique requestId is not used for duplicate-request protection. Missing accounts also are not checked before account.getTransactions().

Path C — balance inquiry

  1. Caller sends POST .../balance?customerId=123.
  2. Controller increments an in-memory counter and creates AccountBalanceQuery.
  3. Service loads all accounts, filters owners by ID, calculates one amount per account, and returns a list of AccountBalanceDTO.
  4. Controller returns the list as JSON.

This path skips a request converter. It also sums all transaction amounts as positive values; because debit amounts are not subtracted, it does not compute a net balance. The counter is process-local and is not a daily window.

9. KYC: an event-driven side path

The intended flow is: a Kafka event says a customer passed or failed verification; CustomerVerificationListener identifies the customer; CustomerVerificationService updates the entity through CustomerRepository.

Kafka KYC event → CustomerVerificationListener → CustomerVerificationService → CustomerRepository → Customer

The event carries identifierType, identifierValue, and verified. The service has handlers for a database ID and national code. The handler currently has important gaps:

  • @KafkaListener is commented out, so this method is not subscribed to the topic.
  • The listener's service field is not injected.
  • The switch cases have no break, so ID falls through to the national-code case.
  • The verification service's repository field is not injected; national-code lookup also lacks a not-found check.
  • Credit/debit do not check whether the customer is verified.

So the classes describe the intended integration, but the active wallet flow does not yet enforce KYC.

10. NotificationService: asynchronous message storage

Credit/debit call notificationService.send(phone, text). The service uses CompletableFuture.runAsync to run a separate task:

CompletableFuture.runAsync(() -> {
    Message messageEntity = new Message();
    messageEntity.setMessage(message);
    messageEntity.setNumber(number);
    messageEntity.setStatus(MessageStatus.PENDING);
    messageRepository.save(messageEntity);
});

This does not send a text message. It only saves a pending message record in the database, asynchronously. The task is not part of the wallet method's database transaction, and an error in the asynchronous task is not returned to the original HTTP request. A complete delivery flow would need a worker or provider integration and status updates.

11. Simple mental model

When reading any endpoint, ask:
1. What HTTP shape enters?
2. Does the controller convert it, or build the application input itself?
3. Which service method runs?
4. Which repository lookup/save happens?
5. Which entity relationship is changed?
6. What response is returned, and what side effects happen separately?

For this project, that method reveals both the intended architecture and the current implementation gaps. It helps explain the system clearly without assuming that every README rule is already enforced.
